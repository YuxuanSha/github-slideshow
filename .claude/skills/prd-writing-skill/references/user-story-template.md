# 用户故事模板

用户故事（User Story）是敏捷开发中描述产品功能的重要方式。本文档提供标准的用户故事编写模板和最佳实践。

---

## 用户故事标准格式

### 基本格式
```
作为 [用户角色]
我想要 [功能/能力]
以便 [获得的价值/解决的问题]
```

### 英文格式
```
As a [user role]
I want [feature/capability]
So that [value/benefit]
```

## 用户故事组成部分

### 1. 用户故事卡片（Card）

#### 示例1：用户注册
```
【用户故事 US-001】

标题: 用户注册账号

作为 一个新访客
我想要 通过邮箱注册账号
以便 我可以登录系统并使用完整功能

优先级: P0 (Must Have)
Epic: 用户认证
估算点数: 5
负责人: @张三
```

#### 示例2：购物车
```
【用户故事 US-015】

标题: 添加商品到购物车

作为 一个已登录的买家
我想要 将心仪的商品添加到购物车
以便 我可以一次性购买多个商品，节省时间

优先级: P0 (Must Have)
Epic: 购物流程
估算点数: 3
负责人: @李四
```

#### 示例3：数据导出
```
【用户故事 US-042】

标题: 导出销售数据

作为 一个运营经理
我想要 导出指定时间段的销售数据为Excel文件
以便 我可以进行离线分析和制作报表

优先级: P1 (Should Have)
Epic: 数据分析
估算点数: 8
负责人: @王五
```

### 2. 对话（Conversation）

用户故事的细节通过团队对话来明确，记录关键讨论：

```
【讨论记录】

Q: 注册时是否需要邮箱验证？
A: 是的，注册后需要点击邮件中的验证链接才能激活账号。

Q: 用户名有什么限制？
A: 3-20个字符，支持字母、数字、下划线，不能以数字开头。

Q: 如果邮箱已被注册怎么办？
A: 提示"该邮箱已被注册"，引导用户找回密码或使用其他邮箱。

Q: 是否支持第三方登录注册？
A: V1.0不支持，V1.1考虑接入微信、支付宝登录。
```

### 3. 验收标准（Confirmation/Acceptance Criteria）

明确的、可测试的标准，用于验证用户故事是否完成。

#### 格式1：Given-When-Then（场景格式）
```
验收标准:

场景1: 成功注册
Given 用户在注册页面
When 用户输入有效的邮箱、用户名和密码
And 用户点击"注册"按钮
Then 系统创建新账号
And 发送验证邮件到用户邮箱
And 显示"注册成功，请查收验证邮件"的提示
And 跳转到登录页面

场景2: 邮箱已被注册
Given 用户在注册页面
When 用户输入一个已被注册的邮箱
And 用户点击"注册"按钮
Then 系统显示"该邮箱已被注册"的错误提示
And 提供"找回密码"的链接
And 不创建新账号

场景3: 密码强度不足
Given 用户在注册页面
When 用户输入的密码少于8个字符
And 用户点击"注册"按钮
Then 系统显示"密码至少需要8个字符"的错误提示
And 不提交表单
```

#### 格式2：清单格式（Checklist）
```
验收标准:

[ ] 用户可以输入邮箱、用户名、密码
[ ] 邮箱格式必须有效（包含@和域名）
[ ] 用户名长度为3-20个字符
[ ] 密码长度至少8个字符，包含字母和数字
[ ] 如果邮箱已被注册，显示错误提示
[ ] 注册成功后发送验证邮件
[ ] 验证邮件包含激活链接
[ ] 点击激活链接后账号状态变为"已激活"
[ ] 注册成功后跳转到登录页面
[ ] 所有错误信息清晰易懂
[ ] 页面响应时间 < 2秒
```

## INVEST原则

好的用户故事应该符合INVEST原则：

### I - Independent（独立的）
用户故事应该是独立的，尽量减少对其他故事的依赖。

❌ 不好的例子：
```
US-010: 实现支付功能（依赖订单系统）
US-011: 实现订单确认（必须先完成US-010）
```

✅ 好的例子：
```
US-010: 用户可以选择支付方式
US-011: 用户可以确认订单信息
```

### N - Negotiable（可协商的）
用户故事是对话的起点，细节可以协商。

✅ 好的例子：
```
作为买家，我想要搜索商品，以便快速找到想要的产品。

（搜索方式、过滤条件、排序规则等细节通过讨论确定）
```

### V - Valuable（有价值的）
用户故事必须为用户或业务创造价值。

❌ 不好的例子：
```
作为开发者，我想要重构数据库架构，以便代码更整洁。
（这是技术任务，不是用户故事）
```

✅ 好的例子：
```
作为买家，我想要查看商品的库存状态，以便决定是否立即购买。
```

### E - Estimable（可估算的）
用户故事应该足够清晰，团队可以估算工作量。

❌ 不好的例子：
```
作为用户，我想要一个更好的体验。
（太模糊，无法估算）
```

✅ 好的例子：
```
作为买家，我想要在商品详情页看到用户评价，以便了解商品质量。
```

### S - Small（小的）
用户故事应该足够小，可以在一个迭代内完成。

❌ 不好的例子（太大）：
```
作为用户，我想要一个完整的电商系统。
```

✅ 好的例子（拆分后）：
```
US-001: 用户可以浏览商品列表
US-002: 用户可以查看商品详情
US-003: 用户可以将商品加入购物车
US-004: 用户可以提交订单
...
```

### T - Testable（可测试的）
用户故事必须有明确的验收标准，可以被测试验证。

✅ 好的例子：
```
作为买家，我想要将商品加入购物车。

验收标准:
- [ ] 点击"加入购物车"按钮后，购物车数量+1
- [ ] 显示"已加入购物车"的提示
- [ ] 商品出现在购物车列表中
```

## Epic、Story、Task关系

### Epic（史诗）
大的功能领域或用户旅程，由多个用户故事组成。

```
Epic: 用户认证系统

包含的用户故事：
- US-001: 用户注册
- US-002: 邮箱验证
- US-003: 用户登录
- US-004: 找回密码
- US-005: 修改密码
- US-006: 退出登录
```

### User Story（用户故事）
从用户角度描述的功能需求。

```
US-001: 用户注册

作为新访客，我想要注册账号，以便使用系统功能。
```

### Task（任务）
实现用户故事所需的技术任务。

```
US-001的任务拆分：
- Task-001: 设计用户表结构
- Task-002: 实现注册API接口
- Task-003: 开发注册页面UI
- Task-004: 实现邮件发送功能
- Task-005: 编写单元测试
- Task-006: 编写集成测试
```

## 用户故事模板

### 模板1：标准用户故事
```markdown
## 用户故事 [US-XXX]: [标题]

**Epic:** [所属Epic]
**优先级:** [P0/P1/P2/P3]
**估算点数:** [1/2/3/5/8/13]
**负责人:** [@负责人]
**Sprint:** [Sprint编号]

### 用户故事
作为 [用户角色]
我想要 [功能/能力]
以便 [获得的价值/解决的问题]

### 背景和动机
[为什么需要这个功能？用户遇到了什么问题？]

### 验收标准
- [ ] 标准1
- [ ] 标准2
- [ ] 标准3

### 设计稿/原型
[附上设计稿链接或原型图]

### 技术说明
[技术实现要点、依赖、约束]

### 测试计划
- [ ] 单元测试
- [ ] 集成测试
- [ ] E2E测试
- [ ] 手动测试用例

### 定义完成（DoD）
- [ ] 代码已提交并通过Code Review
- [ ] 所有测试通过
- [ ] 功能已部署到测试环境
- [ ] PM已验收通过
- [ ] 文档已更新
```

### 模板2：技术故事
```markdown
## 技术故事 [TS-XXX]: [标题]

**类型:** [重构/技术债/性能优化/基础设施]
**优先级:** [P0/P1/P2/P3]
**估算点数:** [1/2/3/5/8/13]

### 问题描述
[当前存在什么技术问题？]

### 解决方案
[计划如何解决？]

### 预期收益
- 提升性能：[具体指标]
- 改善可维护性：[说明]
- 降低技术债：[说明]

### 完成标准
- [ ] 标准1
- [ ] 标准2
- [ ] 标准3
```

### 模板3：Bug修复故事
```markdown
## Bug修复 [BUG-XXX]: [标题]

**严重程度:** [Critical/High/Medium/Low]
**优先级:** [P0/P1/P2/P3]
**影响范围:** [用户数/功能模块]

### Bug描述
[描述bug的现象]

### 复现步骤
1. 步骤1
2. 步骤2
3. 步骤3

### 预期行为
[应该如何表现]

### 实际行为
[实际如何表现]

### 根本原因
[技术原因分析]

### 修复方案
[如何修复]

### 测试验证
- [ ] 验证bug已修复
- [ ] 回归测试通过
- [ ] 相关功能未受影响
```

## 示例：完整的用户故事集

### Epic: 购物车功能

#### US-015: 添加商品到购物车
```
作为 已登录的买家
我想要 将商品添加到购物车
以便 我可以稍后一起结算购买

验收标准:
Given 我在商品详情页
When 我选择了商品规格并点击"加入购物车"
Then 商品被添加到我的购物车
And 购物车图标显示商品数量徽章
And 显示"已加入购物车"的提示
And 提供"去购物车"的快捷按钮

优先级: P0
估算: 3点
```

#### US-016: 查看购物车
```
作为 买家
我想要 查看购物车中的所有商品
以便 我可以确认要购买的商品清单

验收标准:
- [ ] 显示所有已添加的商品
- [ ] 每个商品显示图片、名称、规格、单价、数量、小计
- [ ] 显示购物车总金额
- [ ] 可以勾选/取消勾选商品
- [ ] 显示失效商品（已下架或库存不足）
- [ ] 显示优惠信息（如有）

优先级: P0
估算: 5点
```

#### US-017: 修改购物车商品数量
```
作为 买家
我想要 修改购物车中商品的数量
以便 我可以调整购买数量

验收标准:
- [ ] 可以点击+/-按钮修改数量
- [ ] 可以直接输入数量
- [ ] 数量最小为1
- [ ] 数量最大为库存数量
- [ ] 修改后实时更新小计和总计
- [ ] 超过库存时显示提示

优先级: P0
估算: 3点
```

#### US-018: 删除购物车商品
```
作为 买家
我想要 删除购物车中的商品
以便 我可以移除不想要的商品

验收标准:
- [ ] 每个商品有删除按钮
- [ ] 左滑商品显示删除按钮（移动端）
- [ ] 点击删除后显示确认弹窗
- [ ] 确认后商品从购物车移除
- [ ] 支持批量删除选中商品
- [ ] 删除后可以撤销（5秒内）

优先级: P1
估算: 3点
```

#### US-019: 清空购物车
```
作为 买家
我想要 一键清空购物车
以便 我可以快速移除所有商品

验收标准:
- [ ] 提供"清空购物车"按钮
- [ ] 点击后显示确认弹窗
- [ ] 确认后清空所有商品
- [ ] 显示空购物车状态提示
- [ ] 推荐相关商品

优先级: P2
估算: 2点
```

## 最佳实践

### 1. 从用户角度出发
- ✅ "作为买家，我想要搜索商品"
- ❌ "系统需要提供搜索API"

### 2. 关注价值而非实现
- ✅ "以便我可以快速找到想要的商品"
- ❌ "以便调用Elasticsearch接口"

### 3. 保持简洁
- ✅ 一个用户故事聚焦一个功能点
- ❌ 把多个功能塞进一个故事

### 4. 明确验收标准
- ✅ 使用可测试的、具体的标准
- ❌ "用户体验良好"这种模糊的标准

### 5. 合适的粒度
- ✅ 可以在1-2周内完成
- ❌ 太大（需要几个月）或太小（几小时）

### 6. 包含异常情况
- ✅ 考虑成功场景和失败场景
- ❌ 只描述理想路径

使用这些模板和最佳实践，可以帮助团队更好地理解和实现产品功能！
